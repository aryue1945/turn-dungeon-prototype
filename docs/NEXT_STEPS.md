## 1. Authoritative actor state and grid combat (done)

Add ActorState and GameState with instance IDs, GridPosition, health, facing, equipment and attack/behavior state. Convert combat and occupancy to cells. Preserve existing monster IDs and behavior factories; add stable weapon/tool IDs.

`Scripts/Actors/ActorState.cs` (unique `InstanceId` (Guid), required `DefinitionId`, GridPosition, health, facing, HasPreparedMove, WeaponId/ToolId, Attack reference; engine-independent, unit tested). Player and Enemy both own one as their authoritative source. `ICombatant.GridPosition` replaced pixel `Position`; `AttackResolver`'s offset math and Main's `IsWallAt`/enemy-occupancy sets/spawn-cell selection all work in `GridPosition`. `WeaponDefinition`/`DiggingToolDefinition` (`IEquipment`) carry a stable `Id`, mirrored into `ActorState.WeaponId`/`ToolId`. `Scripts/Game/GameState.cs` exists (Map, Player/Enemies as ActorState references, TurnNumber, Status) and Main keeps it in sync via `AddEnemy`/`RemoveDefeatedEnemies`/`CompleteTurn`/`SetStatus`/`RestoreTurnNumber`.

Acceptance met: rules no longer read node positions; views derive positions from state; definitions remain separate from runtime data; a slow chaser's prepared move is captured explicitly.

## 2. Complete-turn execution (done)

`Scripts/Game/TurnResolver.cs` - `ResolvePlayerAction` resolves the player's half of a turn (attack -> dig -> move/bump) and returns a typed `PlayerActionOutcome`, performing every gameplay mutation itself; tested via `IPlayerTurnActor` and a hand-built `DungeonMap`. `ResolveEnemyAction` wraps one enemy's turn plus door-opening, returning `EnemyActionOutcome` (now also carrying `ActorInstanceId` and, for attacks, an `AttackExecutionDetail`).

`IEnemyMovementBehavior.TakeTurn` returns `EnemyActionResult` instead of `void`; all four behaviors are unit tested against fakes with no Godot node needed. `GameState.IsPlayerDefeated`/`AreAllEnemiesDefeated` are read by `Main.CheckForVictory`/`TakeEnemyTurns` instead of raw actor-list/health fields.

Remaining, deliberately not pursued further: the enemy-phase loop itself stays in `Main.TakeEnemyTurns` rather than moving into TurnResolver behind a pile of delegates - relocating it would not reduce complexity. `ResolveEnemyAction` still takes concrete `Enemy`/`Player` and needs a real node to test itself.

Acceptance met: plain NUnit tests cover complete turns, dead enemies never act, later enemies stop after player death, and each consumed command has exactly one completion boundary even on terminal turns.

## 3. Snapshot capture and turn-history export (done)

`Scripts/Game/GameSnapshot.cs` - `GameSnapshot.Capture(GameState)` deep-copies the map and every actor into independent, serializable objects, including `CellSnapshot.ActorInstanceIds` derived at capture time from the authoritative Player/Enemies lists (never a second source of truth). `Scripts/Game/DebugHistory.cs` keeps the latest 10 transitions plus `BoundarySnapshot`; `GetSnapshotBefore`/`GetLastTransitions` select a menu-sized slice (N transitions plus the one snapshot immediately before them).

The Export button and the "X" key both open a Last 3/5/10-turn export menu (`Main.CreateExportMenu`); opening/using it only toggles UI visibility and reads the already-captured `DebugHistory`, never consuming a turn, mutating `GameState`, or drawing RNG. `DebugHistoryExporter.ToJson(DebugHistory, int, DebugHistoryExportContext)` serializes the selected slice as a `DebugHistoryExport`: schema version, a per-session `RunId`, the dungeon seed, a `FloorId` left `null` (no floor concept yet), a best-effort `BuildVersion`, a `ContentFingerprint` (shared `ContentFingerprinter`, see milestone 5), and compact weapon/monster summaries. Attacks are recorded with attacker id, every cell the pattern swept, and per-target damage/remaining-health/defeated - not a default `(0,0)` target cell.

Remaining, deliberately deferred: no run/floor concept beyond the generated `RunId`/`null` `FloorId` (floors do not exist yet - see roadmap item 11); Main's own wiring (menu open/close, export handlers) has no automated test since Main is a Godot node.

Acceptance met: advancing the live game does not alter past snapshots; at turn 25 the retained states are 15..25; terminal turns are retained; exported JSON explains a blocked/prepared actor with real attack detail; export consumes no turn/RNG.

## 4. Current-run save/resume (done)

`Scripts/Game/GameSnapshotRestore.cs` rebuilds a `DungeonMap` (`RestoreMap`) and an `ActorState`/`AttackState` (`RestoreActor`) from saved data instead of fresh generation/setup. `RunSaveEnvelope`/`RunSaveSerializer` round-trip a versioned save through JSON (`SchemaVersion`, `Seed`, `SavedAtUtc`, a derived `IsComplete`, and - since milestone 5 - `ContentFingerprint`), rejecting an unsupported version or unparsable file with a typed `RunSaveLoadOutcome`. `RunSaveFileService` implements the one current-run save slot plus a recovery backup: `Save` writes and validates a temp file before touching anything already on disk, rotates the existing current save into backup, then atomically replaces current; `Load` falls back to the backup only if it independently validates, never deleting or modifying either file.

`Main.cs`'s boot flow goes `_Ready` -> `RunSaveFileService.Load` -> `ShowStartupMenu`: no resumable save (none exists, or the existing one is already complete) goes straight to New Run; an unfinished one shows Continue/New Run. `OnContinuePressed` resolves the saved WeaponId/ToolId/each enemy's DefinitionId back into real definitions via `TryResolveSaveDefinitions` (checking the run's actual spawn pool, so mods are covered) and compares the current content fingerprint against the saved one - a missing or changed definition disables Continue with a useful error and leaves the save/backup files untouched. `RestoreRun` rebuilds the map, player (`Player.RestoreFrom`) and each enemy (`Enemy.RestoreFrom`) from the snapshot, skipping weapon selection; a save whose status is already Won/Lost goes straight to the end screen. `StartNewRun` confirms first only when the existing save is valid and unfinished. Autosave fires from exactly two call sites - `SelectWeapon` (initial setup) and a shared `FinishTurn` helper both `OnPlayerMoveRequested` branches funnel through - so a turn ending in victory/death produces exactly one save. A keyboard-navigable pause menu (ESC: Restart/Quit/Resume) and Quit buttons round out the flow; Restart from mid-run always confirms first (reusing the same overwrite-confirmation dialog) and skips the stale "resumable save" startup screen on the resulting reload via a one-shot flag.

Remaining: broader manual playtesting of the full flow is roadmap item 1 below - Main is a Godot node, so this wiring has no automated test beyond the pieces it calls.

Acceptance met: save/load plus the next command matches uninterrupted execution; an opened door and destroyed wall stay changed; terminal status persists; corrupt/incompatible saves do not overwrite a valid run; a content mismatch is reported and Continue is refused without touching the save.

Risk carried forward: RNG continuation after loading is explicitly out of scope (see Architecture backlog) - do not promise exact random continuation.

## 5. Reproducible encounter setup and mod compatibility (done)

- **Duplicate-ID detection**: `MonsterModLoader.LoadFromDirectory` tracks which file first defines each id across the whole load pass and disables (naming both files) any later mod file redefining it; `Main.BuildSpawnPool` rejects a mod monster that redefines a built-in id the same way. Regression tests confirm the static registries (`WeaponDefinitions`, `DiggingToolDefinitions`, `MonsterDefinitions`, `EnemyMovementBehaviors`) have no internal collisions.
- **Stable definition ordering**: mod directory/file enumeration is sorted (`StringComparer.Ordinal`) instead of raw filesystem order; `EncounterPlanner.PlanSpawns` sorts the spawn pool by id before any seeded selection, so neither enumeration order nor `BuildSpawnPool`'s built-ins-then-mods concatenation order can change a run's encounter.
- **Seeded enemy selection and placement**: `Scripts/Game/EncounterPlanner.cs` (pure, Godot-free) drives roster and placement from a `System.Random` seeded with the run's own dungeon seed, replacing the previous unseeded `Godot.RandomNumberGenerator`-based placement. Same seed/pool/rooms always produce the same roster, order and positions.
- **Explicit spawn budget**: `EncounterPlanner.DefaultSpawnBudget` (5, matching the previous roster size) decouples enemy count from definition count; a full/exhausted room caps the result instead of throwing.
- **Save-content fingerprint validation**: `Scripts/Game/ContentFingerprinter.cs` is a shared canonicalize-and-hash implementation used by both the debug export's whole-roster fingerprint and `RunSaveEnvelope`'s narrower, run-scoped fingerprint (only the weapon/tool/enemy definitions a specific run actually used, so unrelated content elsewhere can never invalidate an existing save). See milestone 4 for how Continue uses it.

Remaining: acceptance criteria are met at the unit level (`Tests/EncounterPlannerTests.cs` exercises determinism/ordering/budget-capping against synthetic rooms); no full `DungeonGenerator` + `EncounterPlanner` end-to-end fixed-seed integration test exists yet. Per-definition fingerprint diagnostics (identifying exactly *which* definition changed, not just that the combined fingerprint differs) and exported-build mod-folder resolution are deferred - see Architecture backlog.

Acceptance met: same seed/config/content yields the same terrain, roster/order and positions; overfull rooms are handled; saves report incompatible/changed required content clearly.

## Active roadmap

With the architecture foundation done, this is the active direction. Do not add new architecture ahead of what these steps need - pull from the Architecture backlog only when one of them actually requires an item.

1. **Manual verification pass (partially done).** Play through New Run, Continue, the overwrite-confirmation dialog, backup recovery, a terminal (Won/Lost) save's Continue, and the pause menu (Restart/Quit/Resume) in the actual Godot editor. Corruption/backup-recovery and content-mismatch behavior were manually verified; a hand-edited save with an internally-inconsistent health (`Health > MaxHealth`) was found to restore silently instead of being rejected - tracked in the Architecture backlog as "Semantic save validation," deliberately not fixed now.
2. **Explicit Wait command (removed).** Previously shipped as a `wait` input action (Space) -> `Player.WaitRequested` -> `Main.OnPlayerWaitRequested` -> `TurnResolver.ResolvePlayerWait()`. Removed by explicit request; the player no longer has a way to pass a turn without moving, attacking, or digging.
3. **First tactical gameplay slice (done, pending manual playtest).** War Hammer (knockback), Charging Beetle (telegraphed 2-cell charge), a cycling Spike Trap, and one hand-built fixed encounter combining all three. Implemented each mechanic directly against the current turn/state model - no generic forced-movement/effect/hazard framework (see Architecture backlog: "Generalized effect or hazard frameworks").
   - **War Hammer (done).** `AttackDefinition.Knockback` (bool); `ICombatant.Knockback(Vector2)` on Player/Enemy moves exactly one cell, syncing pixel Position and ActorState; `AttackResolver.ExecuteAttack` applies it to a surviving hit target only when the destination is walkable and unoccupied - a blocked push still deals damage. `WeaponDefinitions.WarHammer` (1 damage, one cell forward, same reach as Basic Sword) is selectable in the normal weapon-selection screen (key 3) alongside the fixed encounter.
   - **Charging Beetle (done, revised).** Not a chaser: `ChargingBeetleBehavior` never routes toward the player. Every turn it evaluates two priorities. (1) If the player is within charge range (2 cells) on a clear orthogonal lane (on-axis, no wall in any cell between), it telegraphs for one turn (reusing the exact `ChasePlayerBehavior` prepare pattern - the beetle's "locked intent" needed no new ActorState field, since `Facing`/`HasPreparedMove` already round-trip through `GameSnapshot`/`GameSnapshotRestore`), then charges up to two cells by calling `IEnemyMovementHost.TryMoveForward` twice, stopping early on the existing Blocked/Attacked outcomes - the pre-existing attack-before-move check inside `TryMoveForward` already makes a charge that reaches attack range hit instead of moving onto the target, so no new combat code was needed. (2) Otherwise it wanders: one immediate, untelegraphed step into a random open cardinal direction. The wander's randomness is seeded per-enemy from its spawn `GridPosition` (`Enemy._random`, exposed as `IEnemyMovementHost.NextRandomIndex`) rather than its Guid `InstanceId` or a real-time source, so it stays reproducible for a fixed run without threading a new RNG through `GameState`/`TurnResolver` - not captured across save/resume, matching the already-accepted "exact RNG continuation" gap in the Architecture backlog below. `MonsterDefinitions.ChargingBeetle` (3 health, "Charge Slam" - a dedicated 2-damage one-cell attack, `AttackDefinitions.ChargeSlam`) reuses the Slow Chaser's sprite as a placeholder and is part of the normal built-in roster (`EncounterPlanner`'s spawn budget already decouples roster size from definition count, so this does not change procedural encounter size).
   - **Spike Trap (done).** New `TerrainKind.SpikeTrap` (walkable; reuses the already-existing-but-dormant `TerrainDefinition.ContactDamage`, 1, instead of a redundant new damage field) and a new per-`DungeonCell` `SpikeTrapPhase`/`SpikeTrapPhaseTurnsRemaining` pair, cycling Safe (2 turns) -> Warning (1) -> Active (1) -> Safe via `DungeonCell.TickSpikeTrap`/`DungeonMap.TickSpikeTraps` - real, always-restored state, unlike the dormant TreeWall/GrowingWall regrow timer, which `RestoreState` explicitly still drops. `Scripts/Game/EnvironmentPhaseResolver.cs` (one function, not a generic hazard framework) ticks every spike cell and damages whoever stands on a now-Active one; `Main.RunEnvironmentPhase` calls it once per turn, between `TakeEnemyTurns` and the post-enemy `RemoveDefeatedEnemies`/`CheckForVictory` - after enemy actions, before the turn's snapshot/autosave, and never on a turn that already ended from the player's own action. `CellSnapshot`/`GameSnapshotRestore` carry the phase/timer exactly, so a spike trap mid-cycle survives save/resume and appears in the debug export. `DungeonRenderer` tints the existing floor sprite per phase (gray/yellow/red) rather than needing new art.
   - **Fixed encounter and playtest launcher (done).** `Main.StartFixedEncounter`, reachable only by pressing "F" while the startup screen is showing, hand-builds an 11x7 single room (matching the pattern `Tests/DynamicTerrainTests.cs`/`Tests/SpikeTrapTests.cs` already use for hand-built maps) with one spike trap between the player's and one Charging Beetle's starting cells, force-equips the War Hammer, and skips weapon selection entirely - completely separate from `DungeonGenerator`/`EncounterPlanner`, per the instruction to keep it out of procedural generation until the interaction is proven. Autosave is suppressed for the whole encounter (`_isFixedEncounter`) so playtesting it can never overwrite a real save. Room layout leaves enough open floor on every side of the spike for all three intended strategies: melee the beetle down directly, lure its charge across the spike, or land a War Hammer hit on it while it stands adjacent to the spike to knock it in. No automated test - this is a manual-playtest launcher, matching Main's established untested-glue convention.
4. **Debug scenario editor (in progress).** A separate Sandbox mode entered from the startup screen—not a toggle over an active run—with Edit and Play states controlled by the visible toolbar. Place terrain, enemies and the player from existing definitions, play from that state, Reset back to it, and later save it as a reloadable scenario under isolated storage that can never touch the real save. Full spec: [Debug scenario editor](DEBUG_SCENARIO_EDITOR.md). This comes before the content wave on purpose: the design direction is emergence-first, and emergent combinations cannot be validated by playing procedurally—they have to be constructed, reproduced and replayed after a change. It also retires the hardcoded `Main.StartFixedEncounter` pattern before it multiplies into one method per scenario.
   - **Sandbox mode with Edit/Play states (slice 1, done, pending manual playtest).** `Scripts/Game/ScenarioSandbox.cs` holds the pure state machine (Edit/Play, clamped cell cursor, pixel-to-cell conversion—unit tested in `Tests/ScenarioSandboxTests.cs`); `Main` owns a blank 18x12 room and a keyboard-driven cursor visual, while mouse clicks target tiles directly. Isolation: `_isFixedEncounter` renamed to `_suppressAutosave` and set for the whole session; `CheckForVictory` is skipped entirely while `_inSandbox` (a blank/edited room previously read as an instant win, since zero enemies satisfied `AreAllEnemiesDefeated`).
   - **Terrain palette, placement and actors (slices 2-3, done, pending manual playtest), folded into one pass.** Redesigned per an explicit follow-up request to keep the mode's controls visible: the startup screen shows a "Debug" button alongside Continue/New Run, and Sandbox has a Run/Restart/Reset/Exit toolbar. WASD/arrows move a grid-aligned cursor; Enter/Space opens placement at that cell, while clicking opens it directly on the clicked tile without passive mouse motion overriding keyboard navigation. The object page is a two-column category browser: Enemy, Wall, Ground, and Structure groups are on the left with Player Start, Delete, and Cancel; objects appear on the right, navigated with Right/Enter and Left. Only enemies continue to a facing page; terrain and Player Start apply immediately, and wall orientation belongs to rendering. `ConfirmSandboxPlacement`/`ConfirmSandboxDelete` apply the edit and refresh its cell. Placing over, or deleting, an occupied cell drops any living enemy there from both `_enemies` and `GameState`. Esc returns Play to Edit or closes placement; Exit is a button only. Restart restores the latest play snapshot, Reset restores the initial blank snapshot, and renderer rebuilds clear stale visuals.
   - **Scenario save/load (slice 4, done, pending manual playtest).** A "Save / Load" button on the Sandbox toolbar opens an overlay: a name field plus Save captures the live state (`RunSaveEnvelope.Capture` over `_gameState`/the player's current weapon+tool/each placed enemy's definition) and writes it via `RunSaveFileService.Save`, same as the real save's format; the list below reads back whatever scenario directories exist and Load restores one into Edit. `Scripts/Game/ScenarioStorage.cs` (pure, unit tested in `Tests/ScenarioStorageTests.cs`) is the only thing that resolves a scenario name to a directory - always under `user://scenarios/<name>/`, never `OS.GetUserDataDir()` directly, and it rejects names containing path separators or `..` outright rather than sanitizing them. Loading resolves saved ids back to definitions via the same `TryResolveSaveDefinitions` Continue uses, so a scenario referencing a since-removed mod monster is reported instead of silently restoring wrong. `Main.StartFixedEncounter` and its `F` keybinding are not yet removed - per the spec's acceptance criteria, that happens once its War Hammer/Charging Beetle/Spike Trap scenario is actually rebuilt and saved through the editor, which is a manual follow-up, not this slice.
5. **Scoped player rules: attack, dig, move (proposed, not started).** Source: [Player rules handoff](Claude_Player_Rules_Handoff.md), which reviewed `be1eeba`. This moves the player-side part of step 9's action-dispatch question ahead of that checkpoint, in a deliberately narrow form. Effect propagation and any enemy-side sharing stay at step 9. Enemy decision-making stays in each `IEnemyMovementBehavior`. Enemies may share combat and geometry helpers but do not consume player rules.
   - **Already implemented (keep as-is):** `TurnResolver.ResolvePlayerAction`'s fixed attack -> dig -> blocked -> move order, with its separate `NoAttack`/`Preparing`/`Attacked` results. `AttackOffset` already uses `(Forward, Right)` offsets, e.g. front `(1,0)`, front-left `(1,-1)`. The private `AttackResolver.GetPatternPosition` translates them by facing; do not add a second offset type. Also in place: separate `DetectionOffsets` and `AttackOffsets`, plus `MaxTargets`, `StopsAtWalls` and `AllExceptAttacker`. The player has exactly one `Weapon` and one `DiggingTool`; `EquippedItems`, `PersonalAttackRules` and `ActiveStatuses` do not exist. `AttackExecutionDetail` appears in the debug history. `StatusEffectId` exists, but the resolver does not apply it.
   - **Proposed shape:**
     - **Categories.** Exactly three rule categories: attack, dig and move. No universal event engine, object-pair matrix, global object scan, ECS or generic effect language.
     - **Sources.** Rules stay attached to their source: an equipped weapon, tool or other item, an inherent player ability, or an active temporary status. Unequipped inventory contributes nothing.
     - **Collection.** One small method collects the active rules for a category. It adapts the current `Weapon`/`DiggingTool` slots; do not build a new inventory system for it. The resolver consumes the collected rules without checking concrete item types.
     - **Composition.** Each rule exposes its priority as inspectable metadata. Separately, it declares whether it adds, replaces or cancels. The base is built first, and additive modifiers apply after it: laser 2 plus mushroom 3 gives 5. Ties break by a fixed, documented key. A later modifier cannot undo a cancellation.
     - **No shared mutation.** Each action builds a fresh resolved description. Shared static definitions and their offset arrays are never mutated.
     - **Debug trace.** The existing debug history gains each rule's source, order, condition result, changes and final targets. No replay engine.
   - **Safeguards the implementation must respect:**
     - **Cancellation.** A cancelled action is a terminal outcome, distinct from `NoAttack`. Only a genuine `NoAttack` falls through to dig/move. Document whether each outcome consumes a turn.
     - **Wall blocking.** Today, detection and execution both `break` at the first wall, which blocks the whole pattern. Keep that stop for ordered rays. For surrounding areas, add per-cell filtering. Keep the current sword behavior.
     - **Move timing.** Rules that change reach or permission run before the move is committed. Trail and landing rules run only after a successful move. A failed move fires no success effects.
     - **Prepared attacks.** They keep their locked direction. Do not reset preparation by calling `AttackState.Equip` every action.
     - **Dig splash.** `DigResolver` damages terrain only, and `ICombatant` covers actors only, so splash needs both damage paths. Exclude the player by identity even when the wall is the origin. Do not claim props are damageable until they have a concrete representation.
     - **Persistence.** Statuses persist as stable IDs plus runtime values, never rule objects or delegates. This covers normal saves and scenario saves; save slots stay isolated.
     - **Fingerprinting.** `ContentFingerprinter.DescribeAttack` already omits offsets, `Knockback` and `StatusEffectId`. Decide the save-compatibility impact explicitly before extending it to new geometry or rule data.
   - **Slices, in order:**
     - **(a) Regression coverage (done).** `Tests/WeaponAttackTests.cs` covers Basic Sword, Long Sword and War Hammer in all four cardinal directions, plus a test-only pattern with a nonzero `Right` offset (front-left) to prove `AttackResolver.GetPatternPosition`'s sideways rotation, not just its forward axis. `Tests/TurnResolverTests.cs` covers `ResolvePlayerAction`'s attack, dig-through-breakable-wall, move and wall-blocked branches in all four directions. `GetPatternPosition` stays private and unextracted - these tests exercise it only through the public `AttackResolver`/`TurnResolver` entry points, per the "extract only when a second consumer needs it" rule.
     - **(b) Composition seam.** Add the smallest attack-rule composition seam. Prove it with a test-only additive modifier plus tests for replacement order, ties, cancellation without fall-through, and no shared-definition mutation. No real content yet.
     - **(c) One real mechanic.** Pick one of mushroom status, laser or digger, and settle its open decisions first. It includes persistence, diagnostics and fingerprint handling.
     - **(d) Dig/move composition.** Add it only where (c)'s mechanic requires it.
   - **Open decisions:** settle these before slice (c) for whichever mechanic is chosen.
     - **Mushroom duration.** The request says "20 room"; earlier examples assumed 20 turns. Decide the unit, refresh/stack behavior and the exact expiry boundary.
     - **Prepared-attack modifiers.** Are modifiers captured when preparation starts or recomputed at execution? This matters when a status expires in between.
     - **Laser activation.** Along the beam up to the first wall, or adjacent-only? Hits continue to the wall or map edge either way.
     - **Digger splash.** Four or eight neighbors? Is splash blocked by walls? Does it fire on every successful dig or only when the wall is destroyed? Which objects can it damage?
     - **Area patterns.** What line-of-sight rule applies? Do not choose one silently.
     - **Tie-breaker.** Which key orders rules with equal priority?
6. **Momentum / multiplier.** Continuous effective play raises a multiplier; a wasted action breaks it. This is the system that gives bumping walls to manipulate enemy timing an actual cost, which it currently lacks. Self-contained: a counter on run state, reset conditions, and a HUD readout. Decide what counts as "wasted" before building it.
7. **Weapon geometry as data.** Weapons are distinguished by which cells they hit, not by damage numbers - spear, dagger, whip and the existing swords are all attack-offset patterns. `AttackDefinition` already carries `DetectionOffsets`/`AttackOffsets`/`MaxTargets`/`StopsAtWalls`, so most of this is content plus whatever blocking/target-priority rules non-linear patterns need (define those explicitly - see GAME_DESIGN.md's weapons section). The ray-versus-area blocking split in step 5's safeguards is the same question; settle it once for both.
8. **Trap and terrain set.** Launch/directional tiles, pits, fire, teleporters - implemented directly, following the Spike Trap's shape (per-cell state, ticked in the environment phase, captured in `CellSnapshot`). Same rules apply to enemies wherever sensible: a pushed enemy takes the spike, a charging enemy hits the launch tile.
9. **Effect-system extraction checkpoint.** *Not a build step - a decision point.* After steps 7-8 there will be roughly five concrete mechanics sharing a shape (hammer knockback, spike damage, beetle charge, launch tiles, fire). Only then extract the "attack/effect -> affected cells -> entities on those cells react" pipeline the design calls for, from real cases rather than hypothetical ones. See Architecture backlog: "Generalized effect or hazard frameworks." Two axes meet at this checkpoint, not one. The first is effect propagation, above. The second is action dispatch: resolving one action against one target by the actor's capability rather than by type pair - bumping a wall with no digging tool equipped, for instance. `TurnResolver.ResolvePlayerAction`'s fixed attack -> dig -> blocked -> move chain is the current and deliberate answer to the second axis. Step 5 keeps that chain as the entry point and adds player-scoped attack/dig/move rule collection to it. That is the approved answer for the player. This checkpoint still decides effect propagation and whether any enemy-side dispatch should share it. Two shapes are already rejected: an (actorType, targetType) dispatch matrix (~90% empty cells, and closed to JSON mods, which add capabilities rather than types), and per-object OnBumped handlers (double dispatch leaves resolution order implicit, which deterministic replay and debug history cannot afford). A data-driven predicate/effect rule table is a generic effect language, excluded by Change discipline. Evaluate both axes together here.
10. **Money, shops and NPCs.** Economy tied to the multiplier from step 6; shopkeepers that participate in the simulation (damageable, reactive, able to flee) rather than existing as invulnerable UI. The emergent NPC interactions in the design direction fall out of step 9's pipeline plus ordinary actors - do not script individual outcomes.
11. **Floor-clear objective and exit/transition.** Define what "clearing" a floor means and how the player leaves it. Include floor identity in saves and debug history once floors exist (`RunSaveEnvelope`/`DebugHistoryExportContext`'s `FloorId` is already a `null` placeholder for this).
12. **Expand toward the fuller loop:** multiple floors, three stages, bosses, rewards, a difficulty knob, and basic persistent progression (one unlock, one cosmetic purchase, saved independently of run save/history).

Pause between steps to choose concrete content together - a weapon, an enemy, a hazard - rather than deciding it unilaterally mid-implementation.

## Architecture backlog

Deferred until a concrete gameplay requirement needs them. Do not implement speculatively; each one adds real complexity for a need the roadmap above does not yet have.

- **Per-definition fingerprint diagnostics** - identify exactly which weapon/tool/monster definition changed on a fingerprint mismatch, rather than only "content changed." Needed once mod compatibility errors need to be actionable rather than just accurate.
- **Save migration between schema versions** - `RunSaveEnvelope`/`RunSaveSerializer` currently reject an unsupported version outright rather than upgrading it. Needed once a schema change would otherwise strand existing players' saves.
- **Exact RNG continuation after loading** - Continue currently restores committed state, not in-flight RNG stream position. Needed only if some mechanic's exact random continuation (not just its resulting state) becomes gameplay-visible.
- **Exported-build mod-folder handling** - `MonsterModLoader` resolves `res://mods` via `ProjectSettings.GlobalizePath`, untested against an actual exported (non-editor) build's filesystem layout. Needed before shipping mod support outside the editor.
- **Full replay support** - debug history is inspectable evidence (up to 11 states), not a replay engine. Needed only if replay itself becomes a feature, not a debugging aid.
- **Asynchronous save writing** - autosave currently writes synchronously on the turn-completion path. Needed if save file size or frequency ever causes a noticeable hitch.
- **Generalized effect or hazard frameworks** - implement the first hazard/tactical mechanic directly against the current model (roadmap item 3). Extract a reusable framework only after multiple implemented mechanics demonstrate the same lifecycle - not before.
- **Previous-floor persistence** - unneeded unless backtracking between floors becomes a feature.
- **Complex animation/input-lock handling** - unneeded until animations that could race with input actually exist.
- **Same-direction enemy conga-line blocking** - `Main.TakeEnemyTurns`/`GetOccupiedEnemyPositions` (`Scripts/Game/Main.cs`) resolve enemies sequentially in `_enemies` order, computing each enemy's occupied-cell check from the others' *current, not-yet-updated-this-phase* positions. When several chasers are lined up along the direction they're all about to move (e.g. a 2x2 pack of Slow Chasers all moving toward the player), the trailing enemy's target cell is the leading enemy's not-yet-vacated cell, so the trailing enemy is wrongly `Blocked` while the leading one moves freely - splitting a pack that should move together. Confirmed reproducible with the scenario editor's `s2` save (four `core.slow_chaser` at `(4,5) (4,6) (5,6) (5,5)`, player at `(9,6)`): after one prepare+move cycle the two trailing enemies stay put and the two leading ones advance. Order-dependent on `_enemies`/placement order, so any lined-up same-direction movers can trigger it, not just this scenario. Needs a decision on fix shape before implementing - options discussed: retry blocked-by-enemy cases once more within the same phase before finalizing outcomes (localized), or a larger two-phase "decide all moves, then resolve simultaneously" turn model (see roadmap item 9's action-dispatch axis - this is a related but distinct ordering problem, not the actor/target dispatch one).
- **Semantic save validation** - validate persisted actor health before restoration. Invalid values such as `MaxHealth <= 0`, `Health < 0`, or `Health > MaxHealth` currently restore through `GameSnapshotRestore.RestoreActor`'s constructor/`TakeDamage`-delta behavior instead of being rejected in favor of the backup, the way a schema/parse failure already is. A hand-edited or corrupted-but-valid-JSON save with `Health > MaxHealth` silently ends up at full health rather than triggering the existing invalid-save/backup-recovery path. Consistently edited values (e.g. `30`/`30`) remain restorable and must stay so. Implement when broader save validation becomes necessary - not before, and do not change `TakeDamage`, the current restore logic, or backup recovery to address this in the meantime.

## Change discipline

- Keep documentation aligned with code; mark proposals and disabled experiments explicitly.
- Preserve current rules during architectural refactors; gameplay changes get separate review.
- Run relevant behavior tests for code changes. Documentation changes need link/status checks, not new runtime tests.
- No ECS, global event bus, DI framework, generic effect language or full replay engine.
- Keep full copied snapshots and the existing generator until a concrete requirement justifies more complexity.
- Use a direct implementation for the first instance of a new kind of mechanic; extract a framework only after repetition demonstrates the shared shape.
